# Visual and release gates

This skill can produce consistent *criteria and reusable assets*, but image generation is not pixel-deterministic. Treat model output as a draft until the visual checks pass. Structural scripts cannot certify aesthetics.

## Gate 1: content

- Check every group against the topic's real scope and reliable facts. Keep the owner's flexible animal question framework; do not force a sound question or a fixed group count.
- For new topics, verify first `heading_en` and the rendered cover both read `What`, while the first Q&A uses a complete natural question (for example, `What is a cow?`). Do not copy `What it is` from historical reference art.
- If the topic has a place/location dimension, verify its manifest and rendered cover use `Where` as the heading; keep the natural full `Where ...?` question in Q&A. Do not copy longer location headings from historical reference art.
- If a plant topic has a growth-requirements dimension, verify its manifest and rendered cover use `Needs` as the heading; keep the full natural question with `?` in Q&A. Do not use `What helps it grow` or `What helps them grow` as map headings.
- Build the cover and picture-only coral branches through [branch-topology.md](branch-topology.md), not as uncontrolled image-generation strokes. Trace the actual rendered branch network on each page against the manifest: exactly `N` visible connectors for `N` groups, one endpoint per heading/circle on the cover or picture cluster on the practice page; no additional free curve, fork, or line ending in blank paper. The practice page must contain **no empty circles**. Check the last group explicitly. The branch-plan script cannot detect an old connector left behind in the illustrated base or unwanted circles; visual inspection is still mandatory.
- Show the complete bilingual Q&A and wait for content approval in the owner's one-animal-at-a-time workflow. Freeze `manifest.json` before image production.

## Gate 2: first visual samples

- Before calling image generation, classify the requested output: cover, unlabeled mind-map practice, or complete bilingual Q&A. Reject a prompt for a blank full-page Q&A sheet; “no words” applies to the mind-map practice page, never to Q&A pages. Tool-visible intermediates count as outputs.
- For a full-topic package, produce one complete cover, one **complete bilingual Q&A page with real frozen topic text and final-size illustrations** before batch work. For a requested subset, sample only the formats in scope. A row crop or empty layout does not satisfy the Q&A sample gate.
- Open the actual accepted image files for each format: Cat/Dog cover, Dog/Lion finished picture-only pages, Dog Q&A full pages. Where supported, include the files as image-generation references. Do not rely only on written style adjectives.
- For a home-object topic, also open and pass the exact four owner-approved Window files in `../assets/approved-window/` for the matching cover, practice and Q&A formats. They supersede earlier rejected Window drafts; the selected cover is the original owner-picked image, so do not silently substitute a technically reworked copy.
- Compare the complete Q&A sample page with an accepted Dog Q&A page side by side at full size and phone size. Check header, apparent English size/weight, Chinese legibility, row spacing and page fill, illustration integration, and overall density. If the complete page misses the approved effect, change prompt, composition, art, or layout and re-render before producing the remaining Q&A pages. Record the comparison and result in `prompt-notes.md`.
- When an earlier candidate failed the visual comparison, describe the visible change in the next attempt (for example, main-object pose, vignette mix, type weight, art integration, or row density). A new file with the same failed composition is still a failed candidate even if its structural checks pass.
- Text-free outputs are the mind-map practice page. Every full-page Q&A sample must contain all four bilingual text fields. Select complete-page generation or separate-art typesetting under [production-workflow.md](production-workflow.md), then verify the finished sample before batch production. Never send an auto-displayed, full-page blank Q&A art sheet through image generation. An incidental tool preview of an intermediate must be identified immediately as unfinished.

## Gate 3: every final page

### Cover composition stop gate (also applies in a new chat)

Before promoting a cover candidate, open the actual Key, Cup, selected Cat, and approved Dog covers, plus `assets/approved-carrot/cover-size-reference.png`; save a 300–400 px wide side-by-side comparison with the candidate. Key/Cup control the recognizable topic character and hand-drawn material; Cat/Dog control the whole-page visual rhythm; Carrot controls the **compact left main-subject size**. Apply all four pass questions in [cover-art-direction.md](cover-art-direction.md), recording each answer in `prompt-notes.md`. The candidate must show one prominent but compact subject on the left or center-left and connected groups on the right: each numbered heading is at its branch tip, directly followed by its own small picture studies, with keyword labels beneath those studies. For a typical eight-group page, the subject itself should be about 40–45% of page height and roughly within the left third of page width, while the right groups retain their established size. **A fixed heading/sidebar column separated from a distant icon grid fails, even if the words and icons are individually correct.** Reject a generic main subject, repeated rectangular full-object/room tiles, uniformly heavy or inconsistent linework, a stiff equal-column arrangement, labels over pictures, or type that becomes hard to distinguish at phone width. Do not mark a candidate approved because the manifest, image size, or branch-count scripts passed. If the comparison fails, change the failed visual design and repeat the same-width whole-page comparison before replacing final files or making an archive. Record the specific observed failure and revision in `prompt-notes.md`; remove rejected drafts and their cache copies.

At the start of **each new conversation**, read the on-disk references and this gate again; do not assume earlier chat corrections were retained. A skill invocation is a request to run these checks, not evidence that the generated image already matches the approved series.

| Format | Pass criteria | Reject examples |
| --- | --- | --- |
| Cover | One prominent subject; all manifest groups in order; clear headings and keywords; exactly one purposeful branch connector per group; paper, line, fill and spacing consistent with selected Cat and Dog covers | Keywords on top of pictures, tight rows, unplanned label blocks, missing facts, extra fan/orphan line or missing final connector, different rendering style |
| Picture-only | Compare the exported whole page beside both Dog and Lion finished pages at phone size; recognise the cover artwork; trace one correctly attached connector from the subject to each group's picture cluster; zero readable characters, English hints, numbers and empty circle outlines | Fresh unrelated collage, leftover labels/digits/logo or blank circles, line-free production base presented as a final page, line ending at an old circle, extra/dangling connector, connector ending at the wrong picture group, missing final connector or action arrows |
| Bilingual Q&A | Match the approved Dog whole-page effect at phone size: header, large bold English, readable Chinese, balanced rows/page fill, integrated relevant art, and overall density; adapt row count to real content; all four manifest fields exact | A single matching row inside a mismatched page, self-made template/card colors treated as sufficient, fixed row count that shrinks type, crowded art or excess blank space, Cat-era Q&A style, rectangular art patches, clipped or overlapping text |

- After every newly generated or edited final PNG, run the per-image comparison and inspection in [image-review.md](image-review.md). Check the full raster and record concrete findings for every criterion, every assigned Q&A and every practice connector. A changed image needs a new inspection. Build `review-gallery.html` with `python -X utf8 scripts/build_review_gallery.py <topic-folder>` (add `--home` for home objects); it uses bundled local reference copies and fixed 350 px images, includes applicable Key/Cup/Window/Rabbit references, and generates the final Q&A comparison. Mirror meaningful observations in `prompt-notes.md`. This gallery is a comparison aid, not an automatic aesthetic verdict.
- Export `qa-review-comparison.jpg` after the final Q&A PNG changes. Put one approved full-page Q&A reference and every final topic Q&A page next to each other at the same 300–400 px width; keep this comparison in the internal topic working folder for inspection; exclude it from the learning-image ZIP. Regenerate it whenever a Q&A PNG changes.
- Run `python -X utf8 scripts/check_release.py <topic-folder>` before packaging a full topic. It checks the three image formats, notes, gallery and recorded inspections. Explicitly use `--scope` for a requested subset and read its printed scope. Q&A page ranges follow question IDs, not branch IDs; the checker rejects missing, repeated or out-of-order ranges and missing requested outputs. The compatibility scripts forward to this same checker. A `PASS` does not prove that rasterized text is correct or that a page looks good. Visually confirm all four Q&A fields and the full-page design yourself.
- Release also requires current gallery bindings and [generation evidence](generation-evidence.md): capture actual tool inputs/outputs or local composition/parent recipes and bind later Q&A images to the inspected representative sample. New-topic series must be explicitly declared. Broken links, replaced comparisons and missing/stale evidence fail. Local linkage does not independently authenticate tool execution, and no observer may fabricate records to pass.
- Record unresolved failures in `prompt-notes.md` and revise the affected images. Do not label a package complete, publish it, or create its release archive while a listed page fails.
- Keep only the current candidate while it is being reviewed. Once an image fails or is superseded, delete its topic-folder copy and generated-image cache copy; do not store rejected iterations in `revisions/` or the portable package. Preserve approved reference assets and unrelated outputs. The ordered final files must be unambiguous.

## Portable release

Package the same skill folder, approved references, templates, fonts, scripts and license files on another computer. Follow [../MIGRATION.md](../MIGRATION.md), install `requirements.txt`, and run `python -X utf8 scripts/verify_bundle.py` to verify the unpacked inventory. Validate with `quick_validate.py` when available; test image-reference access and one cover and one complete bilingual Q&A sample before treating migration as working. Use a versioned canonical archive. Another computer needs an image-generation service or tool with reference-image support; no skill file alone guarantees an identical generated picture.
